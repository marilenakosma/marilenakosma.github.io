🏗️ Semantic HTML & Structure

    Use semantic elements over generic containers (<button>, <nav>, <main>, <section>, <article>, <aside>)
    Maintain strict heading hierarchy (<h1> → <h2> → <h3>) with no skipped levels
    One <h1> per page/route; use aria-label on landmarks if multiple of the same type exist
    Never use role="button"/role="link" on <div>/<span>; replace with native elements
    Group related controls with <fieldset> + <legend>
    Provide skip links (<a href="#main-content">Skip to content</a>) as first focusable element

⌨️ Keyboard Navigation & Focus Management

    All interactive elements are reachable via Tab in logical DOM order
    Custom interactive components respond to Enter/Space (not just onClick)
    Visible, high-contrast focus ring on :focus-visible (never remove outline without replacement)
    Focus is trapped in modals, dropdowns, drawers, and popovers
    Focus returns to the triggering element after closing overlays
    tabIndex is never > 0; use tabIndex={-1} only for programmatic focus targets
    Route transitions announce new page titles or move focus to <main> or heading
    Touch targets are ≥ 44×44px (WCAG 2.5.8 / 2.5.5)

🔊 ARIA, States & Live Regions

    First Rule of ARIA: Use native HTML first; ARIA only when semantics are missing
    aria-* states stay perfectly synced with React state (aria-expanded, aria-checked, aria-selected, aria-hidden)
    aria-label is only used when no visible text exists; prefer aria-labelledby with existing text
    Dynamic updates (errors, filters, search results, loading) use aria-live="polite" or role="status"/role="alert"
    Avoid live region spam; batch announcements or debounce rapidly changing state
    aria-busy="true" is set during async operations, removed on completion
    Complex widgets (tabs, trees, grids) use full ARIA pattern implementation, not custom hacks

🎨 Visual, Perceptual & Interaction

    Text contrast ≥ 4.5:1 (normal), ≥ 3:1 (large/UI components) per WCAG 2.2 AA
    Information is never conveyed by color alone (add icons, text, or patterns)
    Support prefers-reduced-motion: reduce (disable non-essential animations, respect user OS setting)
    Layout remains functional and readable at 200% text zoom
    Hover states have keyboard/focus equivalents
    Tooltips are accessible via focus + hover, dismissible, and don’t block content
    Error messages are visible, contextual, and linked to inputs via aria-describedby

⚛️ React-Specific Patterns (2026)

    Use useId() for stable, unique IDs instead of Math.random() or manual counters
    Custom focusable components use React.forwardRef and spread ref + tabIndex correctly
    Client hydration doesn’t break initial accessible markup (RSC-first, progressive enhancement)
    State-driven UI updates don’t cause focus loss or layout jumps that disorient screen readers
    Avoid inline styles that override theme contrast or focus indicators; use design tokens
    Lazy-loaded/suspended content announces loading state and manages focus on resolution
    Virtual lists/grids maintain aria-rowcount, aria-colcount, and row/col indices for AT
    Theme toggles persist user preference and respect prefers-color-scheme as fallback

🧪 Testing & Validation Pipeline

    eslint-plugin-jsx-a11y enabled with error level, no rule overrides without justification
    axe-core or @axe-core/react runs in dev, CI, and Storybook
    Lighthouse a11y audit ≥ 95 in CI; failures block merge
    Manual keyboard-only testing per page/flow
    Screen reader testing: VoiceOver (macOS/iOS), NVDA (Windows), TalkBack (Android)
    Automated E2E tests include focus/assertion checks (cy.focused(), toHaveAttribute('aria-expanded', 'true'))
    Storybook + @storybook/addon-a11y for component-level audits
    Real disabled user testing in UAT (not optional)

🧠 Workflow & Mindset

    Accessibility is treated as a functional requirement, not a post-launch fix
    PR templates include a11y checklist + testing notes
    Design system tokens enforce contrast, focus, spacing, and motion constraints
    useId, useFormStatus, useOptimistic, etc. are audited for a11y implications
    Documentation includes keyboard shortcuts, screen reader behavior, and known limitations
    Team tracks a11y debt in backlog with severity labels (a11y-blocker, a11y-minor)
